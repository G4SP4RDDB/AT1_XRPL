# Friction log — raw findings (append-only, both people)

Header for the report: **Track 1, open-ended** · flavour: Vanilla (multisig enforcer is a candidate Loaded composition) · environment: custom hackathon devnet `lending-hackathon.dev.ripplex.io` (rippled 3.4.0-rc1, reserve 10 XRP base + 2 XRP per object) · library: `xrpl.js 5.2.0`.

| # | Category | Title | Description | Repro | Severity | Library + version | Proposed fix |
|---|---|---|---|---|---|---|---|
| 1 | docs / wrong model | `LoanDraw` does not exist | Hackathon material and our own docs assumed a separate drawdown transaction. Principal moves when `LoanSet` validates. | `node_modules/xrpl/dist/npm/models/transactions/` has no loanDraw | medium | xrpl.js 5.2.0 | XLS-66 overview: state that `LoanSet` originates and disburses in one transaction; add a lifecycle diagram listing every transaction type by stage |
| 2 | protocol / wrong model | Open-ended vault liquidity is not a lock | Coupons and later deposits refill `AssetsAvailable`; withdrawals are first come first served, so a depositor can pull principal out of coupon liquidity. | to reproduce in S2 | high | xrpl.js 5.2.0 | `AssetsMaximum` at creation as workaround; XLS-65 docs should describe how `AssetsAvailable` evolves through the loan lifecycle; propose a principal-locked shares flag |
| 3 | protocol / workaround | No earliest-close term on `LoanSet` | The protocol prices an early close (`CloseInterestRate`, `ClosePaymentFee`) but cannot forbid it before a date, so a bond-like product needs a trusted co-signer. | S1 Q2 | high | xrpl.js 5.2.0 | Optional earliest-close ledger time on `LoanSet`, enforced by the ledger |
| 4 | infra | Venue network drops TLS on ports 51233 / 51234 | TCP connects but the TLS handshake never completes on any rippled port, including `s1.ripple.com:51234`; port 443 works. The faucet (443) is fine. | `curl -v https://lending-hackathon.dev.ripplex.io:51234` stalls after Client Hello | high (blocks all on-chain work on venue wifi) | n/a | Expose the hackathon devnet WSS and JSON-RPC on 443 as well; tell participants up front |
| 5 | sdk | `Client` option is `connectionTimeout`, not `timeout` | `new Client(url, { timeout })` compiles (it is the request timeout) but does not extend the 5 s connect timeout; the error text names the right option only after the fact. | `src/chain/client.ts` first version | low | xrpl.js 5.2.0 | Name the two timeouts distinctly in the `Client` docs, or default connect timeout higher |
| 6 | docs / broken | Workshop slide tutorial link 404s | The intro deck's "Step-by-Step Lending Walkthrough" points to `xrpl.org/docs/tutorials/lending`, which returns 404. The XLS-65/66 specs on GitHub and the reference app README are the working sources. | `curl -I https://xrpl.org/docs/tutorials/lending` | low | n/a | Fix the slide link or publish the tutorial at that path |
| 7 | protocol / wrong model | PPS rises at origination, not per coupon | `LoanSet` books the whole `InterestDue` into `Vault.AssetsTotal` at once (XLS-66 §3.8.6). Coupons only refill `AssetsAvailable`. Our design, and the workshop slide 12 ("Borrower repays, PPS rises"), assumed PPS moves with each payment. | XLS-66 §3.8.6 item 6; to observe in S2 | high | xrpl.js 5.2.0 | Say it explicitly in the XLS-66 overview and slide 12: yield is recognised at origination and realised as liquidity with each `LoanPay`; expose `InterestDue` in `vault_info` |
| 8 | protocol / expectation | `AssetsMaximum` blocks origination | A cap equal to the raise makes `LoanSet` fail with `tecLIMIT_EXCEEDED` because origination adds `InterestDue` to `AssetsTotal` and the cap must exceed `AssetsTotal + InterestDue` (§3.8.5.2 items 6, 14). The result code does not say which of the two cap checks failed. | to reproduce in S2 | medium | xrpl.js 5.2.0 | Document that the cap must include expected interest; distinct result code or `vault_info` field showing the required headroom |
| 9 | docs / gap | Annualised rates make short test loans earn almost nothing | Rates are 1/10 bp annualised with a 60 s minimum interval. A 9-minute 1000 XRP loan at the 100 % maximum earns ~0.017 XRP, and small principals hit `tecPRECISION_LOSS` (§3.8.5.2 items 15-18). Nothing in the docs warns that devnet demos need large principals or long intervals. | config maths, to confirm in S1 | medium | xrpl.js 5.2.0 | A "testing on devnet" note with worked numbers; an SDK helper that computes `PeriodicPayment` and `InterestDue` before submitting |
| 10 | protocol / error message | `VaultDeposit` of the whole balance fails as `tecINSUFFICIENT_FUNDS` | Lender held exactly 1000 XRP and deposited 1000. The devnet reserve is 10 XRP base + 2 per object, and the deposit also creates the share `MPToken` object, so the real cause is reserve, not funds. The code does not say so. | tx 90E991C72D74 (spike run 1) | low | xrpl.js 5.2.0 | Return `tecINSUFFICIENT_RESERVE` when the shortfall is the reserve; SDK pre-check that subtracts reserve + new-object reserve before submitting |
| 11 | sdk / expectation | `signLoanSetByCounterparty` `multisign` string means the signer's X-address, not the multisig account | Passing the borrower account address as `multisign` (the natural reading: "sign on behalf of this multisig account") set `Signer.Account` to the borrower for both signers, so the SDK rejected the combined transaction with "Duplicate Signers not allowed". The boolean form is the correct one; the string is only for X-addresses of the signer itself, the same convention as `Wallet.sign`. | spike run 1, step 5 | medium | xrpl.js 5.2.0 | Name the option `signerXAddress` or document it inline; validate that Signers accounts are distinct with a message naming the option |
