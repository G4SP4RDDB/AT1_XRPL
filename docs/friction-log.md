# Friction log — raw findings (append-only, both people)

Header for the report: **Track 1, open-ended** · flavour: Loaded (native 2-of-2 multisig composed as the call-date enforcer on the final `LoanPay`) · environment: custom hackathon devnet `lending-hackathon.dev.ripplex.io` (rippled 3.4.0-rc1, reserve 10 XRP base + 2 XRP per object) · library: `xrpl.js 5.2.0`.

| 8 | protocol / expectation | `AssetsMaximum` blocks origination | A cap equal to the raise makes `LoanSet` fail with `tecLIMIT_EXCEEDED` because origination adds `InterestDue` to `AssetsTotal` and the cap must exceed `AssetsTotal + InterestDue` (§3.8.5.2 items 6, 14). | 9 | docs / gap | Annualised rates make short test loans earn almost nothing | Rates are 1/10 bp annualised with a 60 s minimum interval. | 12 | protocol / expectation | `LoanManage` impair refused with `tecTOO_SOON` on a current loan | With `fixCleanup3_4_0` active, `tfLoanImpair` is only accepted once `currentTime > NextPaymentDueDate`. | 13 | docs / gap | Where each loan fee goes is not summarised | The early close sent the 1 % `CloseInterestRate` penalty to the vault (PPS 1.0000056 to 1.0066) and the 1 XRP `ClosePaymentFee` to the broker; `ManagementFeeRate` skims the interest of each coupon (57 of 5709 drops). This is scattered across §3.11.5 and Appendix A-3, no single table. It matters because `CloseInterestRate` turns out to be a ledger-enforced economic yield lock for bond-like vaults. | LoanPay full 685A52185C45: offered 681001942, charged 674.335291 XRP | medium | xrpl.js 5.2.0 | One "fee destinations" table in XLS-66: fee, who pays, who receives, when |
| 11 | sdk / expectation | `signLoanSetByCounterparty` `multisign` string means the signer's X-address, not the multisig account | Passing the borrower account address as `multisign` (the natural reading: "sign on behalf of this multisig account") set `Signer.Account` to the borrower for both signers, so the SDK rejected the combined transaction with "Duplicate Signers not allowed". The boolean form is the correct one; the string is only for X-addresses of the signer itself, the same convention as `Wallet.sign`. | spike run 1, step 5 | medium | xrpl.js 5.2.0 | Name the option `signerXAddress` or document it inline; validate that Signers accounts are distinct with a message naming the option |
| 14 | protocol / expectation | Full repayment after the call date fails with `tecEXPIRED` | Once a scheduled payment is overdue, `LoanPay` needs `tfLoanLatePayment`, and that flag is mutually exclusive with `tfLoanFullPayment`, so an overdue loan cannot be closed in one transaction: the late coupon must be cleared first. Also, the call date is by construction the last due date, so "final repayment at the call date" is the last regular coupon, and `tfLoanFullPayment` only ever means an early close. Our first implementation sent a full payment after the call date. | LoanPay 0CAB4645F86B (demo close run 3) | medium | xrpl.js 5.2.0, rippled 3.4.0-rc1 | Docs: a "how to close a loan" section covering on-time, late and early cases; consider letting `tfLoanFullPayment` settle overdue amounts in one transaction |
| 15 | protocol / security gap | Multisig lacks on-chain time restrictions, forcing 2nd key to be 100% software-governed (Zero-Human access) | XRPL `SignerListSet` defines *who* can sign, but has no native temporal semantics (no `SignAfter` or `ValidAfter` per-signer rule). For an AT1 bond requiring a strict Call Date, the 2nd signature must be held by an autonomous software daemon where **zero human access is allowed**; otherwise any human keyholder could unilaterally break the bond maturity. | S1 Q1 & Enforcer implementation | high | Core XRPL Multisig / XLS-66 | **Proposed fix**: 1) Native `SignerCondition` in `SignerListSet` allowing time-based eligibility (e.g. `SignAfter: rippleEpoch`); 2) In the interim, run the software enforcer daemon inside a hardware-isolated Confidential Enclave / HSM (e.g. AWS Nitro Enclave) with zero human operator keys. |
| 16 | sdk / dead_end | WalletConnect cannot address a custom network | xrpl-connect's WalletConnect adapter identifies the ledger by a CAIP-2 id and only knows `xrpl:0/1/2` (mainnet/testnet/public devnet). Pairing asks for `xrpl:2`, WalletConnect v2 downgrades required namespaces to optional, the wallet approves only the chains it supports, and every sign request is then rejected client-side with `Failed to sign transaction. Missing or invalid. request() chainId: xrpl:2` before the wallet sees it. | `frontend/src/lib/xrplConnect.ts` (`signPrepared`), session namespaces vs `hackathonDevnet.walletConnectId` | high (blocks every wallet signature on the devnet) | xrpl-connect 0.8.2, @walletconnect/sign-client bundled | A CAIP id convention for custom networks (`xrpl:<NetworkID>`), and a documented `network` object with node URLs that adapters honour; pick the request `chainId` from the approved session namespaces instead of the configured one |
| 17 | sdk / expectation | `WalletConnectAdapter.sign()` returns the bare signature as `tx_blob` | `sign()` sends `xrpl_signTransaction` with `autofill: true` hardcoded and returns `{ tx_blob: tx_json.TxnSignature }`: the signature hex, not a serialized transaction, so `submit(tx_blob)` can never work. `signAndSubmit()` has the same shape. | `node_modules/xrpl-connect/index-*.mjs`, `requestSignTransaction` / `sign` | high | xrpl-connect 0.8.2 | Return `encode(tx_json)` as `tx_blob`; expose `autofill` as an option (an app that autofilled for a custom network, NetworkID included, must be able to say `autofill: false`).
